9008 进法（多个来源一致）
--------------------------
  * OPPO 自 R7 起不提供 fastboot；R9s/R9sk 无法用 fastboot 解锁。
  * 首选：关机 -> 同时按住 音量+ 和 音量- -> 插入 USB ->
    QUSB_BULK/9008。
  * 后备：深刷线（D+ 绿线短接 GND 黑线，带开关）或拆机短接尾插/主板 TP。
    关机插线，短接 3-5 秒后断开；看到 9008 端口就立即断开短接。
    来源：https://cnblogs.com/sztom/p/10352957.html

      http://www.romleyuan.com/lec/read?id=142
      https://cnblogs.com/zerofc/p/12263007.html

替代工具链（不碰改版 exe，研究级）
------------------------------------
  * bkerler/oppo_decrypt 的 ofp_qc_decrypt.py：从 OFP 提取
    prog_firehose_ddr.elf（签名 loader）。
      https://github.com/bkerler/oppo_decrypt
      https://github.com/unix3dgforce/OppoDecrypt
  * bkerler/edl：Sahara/Firehose 客户端。
      https://github.com/bkerler/edl
  * HsOjo/edl-noauth-kit：针对 2018+ 需要 sig auth 的 loader。
    原理：全新 9008 会话里 challenge 为空，比较循环被跳过，
    blob2（256 字节）可过；每次操作前必须重新进 9008。
    该 kit 在 macOS 测试（SDM660），Windows 未实测。
      https://github.com/HsOjo/edl-noauth-kit
  * QFIL / QSaharaserver + fh_loader：XDA 有 OPPO R9s 的案例标题
    （"Use QFIL or Windows 7 64-bit command line tool + QSaharaserver.exe
    + fh_loader.exe ... to OPPO R9s"），正文返回 403，细节未核实。
    原理上可直接用 OFP 里的 rawprogram0.xml + 签名 firehose，
    不依赖 OPPO 的 MsmDownloadTool 授权。仅作线索。

CVE-2021-1905（补充）
---------------------
  P0 RCA 明确：Proof-of-concept N/A，exploit sample N/A。
  触发条件：
    1) 一个 GPU 共享映射被拆成多个 VMA；关闭其中一个 VMA 会调用
       kgsl_gpumem_vm_close，清空 entry->memdesc.useraddr；
    2) get_mmap_entry 因此允许再次映射；
    3) fork 出的两个进程共享 GPU 地址空间，在 kgsl_get_unmapped_area
       里竞态。
  3.18 有对应状态错误，但没有公开利用；属研究题，不是交付路径。
      https://googleprojectzero.github.io/0days-in-the-wild/0day-RCAs/2021/CVE-2021-1905.html

Firehose loader 离线核验（2026-11-21 20:35）
--------------------------------------------
下载自 OneLabsTools/Programmers（经 jsDelivr / raw.githubusercontent）：

  文件名                                     大小      MD5
  prog_emmc_firehose_8953_ddr_oppo_r9s.mbn   359048    1ded75bb22c4e9334462f8be717ac907
  prog_emmc_firehose_opp_r9s.mbn             359048    1ded75bb22c4e9334462f8be717ac907  （与上一行同一文件）
  prog_emmc_firehose_8953_oppo_r9s.mbn       359112    e0165a731ebb573aa66be7c99023264c
  prog_emmc_firehose_8953_ddr.mbn            359048    6e7aac18a7df36697e18a8cc0081ce70
  prog_emmc_firehose_8953_ddr_oppo.mbn       359064    4f343a2745beed6593e82e52d8ca05bd
  MSM8953.mbn                                363164    333fbe3da5a85898abde77fe03ad4988

  * 前三个是 ELF32（e_machine=0x28 / ARM），是真正的 Firehose programmer。
  * prog_emmc_firehose_8953_ddr_oppo.mbn 开头是 ASCII "data ddc,"，不是 ELF，
    也没有 Firehose 命令字符串；疑似误标/非 programmer，不可用。
  * MSM8953.mbn 内嵌 "Xiaomi Attestation CA0 / Xiaomi Root CA 10"，是小米签名，
    对 OPPO 不可用。

Temblast 索引交叉核对（https://www.temblast.com/ref/loaders.htm）：
  * 1ded75bb22c4e933 行：Signer=Oppo，SHA256=90864ecb91f86a1c，
    SHA384=ca93d5300bc053d7，ELF32。
  * 6e7aac18a7df3669 与 e0165a731ebb573a 也在同一个 Oppo 签名组
    （90864ecb91f86a1c / ca93d5300bc053d7）。
    → 这批 OPPO 8953 loader 共用同一张 OPPO 根证书，不是按项目号各签一份。
  * temblast 收录的 2745 个 loader 中没有 r9sk / 16027 文件名；
    也没有第二个 OPPO 8953 签名组。

二进制内容：
  * 三个 ELF32 loader 均含完整 Firehose 命令：
    configure / getstorageinfo / program / erase / patch / peek / read /
    firmwarewrite / erasecust
  * 均无 "Only nop and sig tag can be received before authentication"；
    即没有 2018+ loader 的 Firehose 二次认证门。
  * 证书字符串均为 "General OPPO 16017 Root CA1" /
    "General OPPO 16017 attestation CA1"，没有 16027。

判定（推断，待 9008 实测）：
  * 公开可得的是 R9s（16017）签名的 8953 全功能 loader；R9sk（16027）
    专用 loader 在公开 loader 索引中不存在。
  * R9sk 与 R9s 同属 CPH1607 家族，设备 OTA 字符串是
    R9s_11.A.37_0370_201911271523，固件基线共用；因此 R9sk 很可能接受
    同一 OPPO 根证书签名的 loader。
  * Sahara 是否接受，最终取决于设备 QFPROM 里的 PK_HASH；只有进 9008 用
    edl / QSaharaServer 握手才能证实。若拒绝，回退到 R9sk A.18/A.22 包内
    loader（A.18 1.53GB，MD5 8171554911a97008e410b385667fc9f2；
    A.22 1.30GB，标题明确带 firehose_8953）。
  * 该 loader 没有 Firehose 二次认证门；若 Sahara 通过，bkerler/edl 可直接
    执行 configure / program / read，不需要 HsOjo noauth kit。
